Scan Operators

Combine filtering, projection, and products, then measure how early filtering reduces candidate pairs in a join.

1 · CREATE records a schema and its layout

CREATE TABLE students (sid INT, name VARCHAR(8), gpa INT, mid INT);
CREATE TABLE majors (mid2 INT, dept VARCHAR(8));
schema = (Schema().add_int_field("sid")
                  .add_string_field("name", 8)
                  .add_int_field("gpa")
                  .add_int_field("mid"))
catalog.create_table("students", schema)
students_layout = catalog.get_layout("students")

schema = Schema().add_int_field("mid2").add_string_field("dept", 8)
catalog.create_table("majors", schema)
majors_layout = catalog.get_layout("majors")

Schema describes the fields. Catalog.create_table() computes a Layout and inserts ordinary records into table_catalog and field_catalog. get_layout() scans those records to reconstruct the offsets and slot size. The first TableScan on students creates its data file and first block.

students_layout.slot_size == 28. A 128-byte block holds four student slots, with 16 bytes left over. Field f in slot k starts at byte k * 28 + students_layout.offset(f) within its block.

The corresponding catalog records are ("students", 28) in table_catalog and ("students", "sid", "int", 0, 4), ("students", "name", "varchar", 8, 8), ("students", "gpa", "int", 0, 20), and ("students", "mid", "int", 0, 24) in field_catalog. Its columns are (tblname, fldname, fldtype, length, offset).

In this storage API, the string capacity is UTF-8 bytes; eight non-ASCII characters may need more than eight bytes. Our names use ASCII. GPAs are stored in tenths: 39 represents 3.9. These examples do not add SQL constraints or transaction handling.

2 · INSERT reserves a slot, then writes its fields

INSERT INTO students (sid, name, gpa, mid) VALUES
  (1, 'ada', 39, 1), (2, 'ben', 31, 2), (3, 'cyd', 37, 1),
  (4, 'dee', 28, 3), (5, 'eli', 36, 2), (6, 'fay', 34, 1),
  (7, 'temp', 40, 1);
rows = [(1, "ada", 39, 1), (2, "ben", 31, 2), (3, "cyd", 37, 1),
        (4, "dee", 28, 3), (5, "eli", 36, 2), (6, "fay", 34, 1),
        (7, "temp", 40, 1)]
students = TableScan(bm, fm, "students", students_layout)
try:
    for sid, name, gpa, mid in rows:
        students.insert()                 # mark a free slot USED; position on it
        students.set_int("sid", sid)       # write within that slot
        students.set_string("name", name)
        students.set_int("gpa", gpa)
        students.set_int("mid", mid)
        print(name, students.rid())        # (block number, slot number)
finally:
    students.close()

Ada occupies (0, 0), Ben (0, 1), Cyd (0, 2), Dee (0, 3), Eli (1, 0), Fay (1, 1), and Temp (1, 2). insert() searches for an empty slot after the cursor, moving to or appending another block when necessary. Setters use the layout to write the current slot and mark its buffered page dirty.

3 · DELETE finds a row and clears its slot flag

DELETE FROM students WHERE sid = 7;
students = TableScan(bm, fm, "students", students_layout)
try:
    students.before_first()
    while students.next():
        if students.get_int("sid") == 7:
            print("deleting", students.rid())  # (1, 2)
            students.delete()                # current slot's flag becomes EMPTY
finally:
    students.close()

TableScan.delete() calls RecordPage.delete(current_slot). It changes the flag from 1 to 0; it does not shift other rows or erase the old field bytes. Future scans skip that slot. An insertion can reuse it when its free-slot search reaches it.

The six original students remain. The loop checks every live row because this schema declares no uniqueness constraint on sid. This update uses the writable TableScan directly; the new query wrappers expose the read-only scan interface.

4 · SELECT constructs a plan, then pulls rows

SELECT name FROM students WHERE gpa > 35;
source = TableScan(bm, fm, "students", students_layout)
selected = SelectScan(source, Predicate(("gpa", ">", 35)))
plan = ProjectScan(selected, ["name"])
try:
    plan.before_first()
    while plan.next():
        print(plan.get_val("name"))
finally:
    plan.close()  # delegates down to source.close()

Plan: Project(name) ← Select(gpa > 35) ← TableScan(students). Calls travel from the root to its inputs; accepted rows are exposed back up the tree. The first root next() finds Ada. The second skips Ben and finds Cyd; later calls find Eli, skip Fay and the deleted slot, then report exhaustion.

Output: ada, cyd, eli. The projection belongs above selection because the filter needs gpa, while the output exposes only name. These snippets run once you implement the operators below. The shown order follows this scan; SQL without ORDER BY does not promise an order.

5 · JOIN combines a product, a predicate, and a projection

SELECT name, dept
FROM students JOIN majors ON mid = mid2
WHERE gpa > 35;
students = TableScan(bm, fm, "students", students_layout)
majors = TableScan(bm, fm, "majors", majors_layout)
pairs = ProductScan(students, majors)
matched = SelectScan(pairs, Predicate(("mid", "=", F("mid2")),
                                      ("gpa", ">", 35)))
plan = ProjectScan(matched, ["name", "dept"])
try:
    plan.before_first()  # initialize both product cursors
    while plan.next():
        print(plan.get_val("name"), plan.get_val("dept"))
finally:
    plan.close()         # recursively closes both table scans

Output: (ada, ds), (cyd, ds), (eli, stat). F("mid2") reads the right row’s field; plain "mid2" would compare mid with a string literal. The distinct names mid and mid2 let the product route each field correctly; this API has no SQL table aliases or qualified-name resolution.

One plan, two inputs, three matching rows

Project(name, dept)
        ↑
Select(mid = mid2 AND gpa > 35)
        ↑
ProductScan
    ↑                    ↑
TableScan(students)   TableScan(majors)

Each request at the root makes the product enumerate pairs until the selection accepts one. Ada is paired with DS, Stat, and Econ before the left cursor advances to Ben. Six students × three majors produces 18 candidate pairs; the predicate keeps three. The product holds the current pair instead of constructing an 18-row intermediate table. The measurement later moves the GPA filter below the product to reduce this work.

How each operator uses its input scans

Each operator refers to its input scan or scans and implements the same five methods. These operators expose one current row at a time without storing a copy of the full result. Their memory use depends on the plan and its active scans, rather than the number of result rows. The table shows which behaviors each operator changes.

OperatorChangesDelegates untouched
SelectScannext: skip until the predicate passeseverything about row shape
ProjectScanget_val / has_field: answer only for kept columnseverything about row flow
ProductScanall five: it has two childrennone; it coordinates two inputs

Control flow for the scan operators

The annotated sketches below describe the control flow; they are not executable Python. Handle empty inputs. Once ProductScan.next() returns False, it must keep returning False until the product is rewound.

SelectScan.next: while scan.next(): if pred.is_satisfied(scan): return True
ProjectScan.get_val: raise ValueError unless fld in self.fields
ProductScan.before_first: left rewind + next · right rewind
ProductScan.next: right.next() or (right rewind · left.next() and right.next())
ProductScan.get_val: ask the side whose has_field says yes
Hover a line: if you can explain each one aloud, you are ready to implement the operators.

Join conditions need no new machinery: a predicate term's right side may be F("mid2") (a field instead of a literal), and Predicate.is_satisfied (provided) already handles it. The cartesian product plus that predicate is the join.

Common implementation mistakes

In ProductScan.before_first, rewind both children and store the result of left.next() in self._left_ready. The unit tests use this shared state to test before_first and next independently. During iteration, advance the right child; when it is exhausted, rewind it and advance the left child, updating self._left_ready. Keep it false once either input is exhausted and no pair remains. Finally, close() must close both children so their buffer pins are released.

Exercise · read the failure

A classmate’s product has before_first() rewind both children, but does not advance the left child. Its first next() advances the right child. Why is the resulting pair invalid?

Show answer

The left scan is still before its first row, so there is no valid left value to pair with the right row. Rewind both children, advance the left once, and remember whether that advance succeeded. If either input is empty, the product must return no rows.

Filtering before the product reduces the number of pairs examined by a factor of 15 in this example, while returning the same rows. The right input is scanned once per left row, so input order also affects the work. Caching the inner input can reduce repeated reads; Lecture 9 introduces hash joins as another way to avoid enumerating every pair.

A pandas merge materializes its result, so joins with many matches can require much more memory than either input. An equality merge does not normally build the full Cartesian product. Our ProductScan does enumerate every pair, but streams them one at a time. Filter placement matters in both approaches.

Python generators use a similar pull-based model. Calling next(generator) resumes execution until the next yield, which returns a value to the caller. A chain of generators can therefore pass one row at a time through several processing steps.

Polars’ lazy API and Spark DataFrames describe computations as plans. An action such as collect() executes the plan. Their optimizers can move a filter closer to its input when doing so preserves the result. In distributed processing, filtering before a shuffle can also reduce the rows sent across the network.

FAQ

My join returns 18 rows, not 3.

Check that the plan places the join’s SelectScan above ProductScan and that SelectScan.next() evaluates the predicate before returning a row. The product generates 18 pairs; the selection must keep only the three that match.

My join returns 0 rows but cardinality passes.

Check field routing first. ProductScan.get_val("mid2") must ask the child that contains mid2. Use each child’s has_field method to choose which child supplies the value.

Does the order of terms inside a Predicate matter?

For correctness, no: it's a conjunction. For speed, mildly: is_satisfied stops at the first failing term, so putting the cheapest, most-often-failing test first saves comparisons. Real optimizers reorder terms for exactly this reason.

Why "left wins ties" instead of an error on ambiguous fields?

Microdb checks the left input first when both inputs have the same field name. The tests avoid that ambiguity. SQL normally requires a qualified name such as students.id when an unqualified reference is ambiguous; supporting that would require a name-resolution layer beyond this lab.
